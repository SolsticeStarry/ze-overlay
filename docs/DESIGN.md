## 1. 现状

**CS2（ZE 模式）神器列表识别 + 点击穿透叠加**，C# / .NET 8 + WPF，识别用 **PP-OCRv3 ONNX**。

代码按**数据管线阶段**划分为 14 个模块（清单见 `AGENTS.md`「代码分层」）：

```
S0 采集 → S1 行分析 → S2 字形/裁剪 → S3 识别 → S4 解析 → S5 跟踪 → S6 名单匹配 → S7 展示
```

| 里程碑 | 状态 |
|---|---|
| M0 截屏 + ROI + 预览 | ✅（像素级验证） |
| M1 行切分 + 翻页检测 | ✅（翻页判据真机验证） |
| M2 字形识别 | ✅（字形切分目视验证） |
| M3 跟踪 + 外推 | ✅（行槽位身份） |
| M4 名称 OCR + 名单匹配 | ✅（阈值实测校准） |
| M5 交互层 | ✅ 穿透叠加 / 设置面板（常驻预览左列：名单·显示·频率·热键）/ 名单增删 / 一键加入 |
| M6 性能与打包 | 🟡 识别 12 行 **602ms → ~70ms**（DML + 固定宽 + 全批）；**自包含单文件夹 + 单文件自解压安装器已完成**（`PACKAGING.md`）；**int8 静态量化已实测否决**（§3.1/§5） |

- 构建 **0 警告 0 错误**；单测 **293 / 293**。
- 实测效果：**13 个神器 ↔ 13 条跟踪，零重复**；倒计时 1s/1s 递减，归零转 `[R]`。
- 已支持**多社区服档案**：本服（括号语法、有翻页）与一个社区服（Plain 语法、无翻页）共存，
  运行时按神器名自动选档，见 §3.8。

## 2. 用户指令 → 处置

| 用户要求 | 处置 | 依据 |
|---|---|---|
| 语言选型按「**快 + 低占用**」 | **C# / .NET 8**，删掉旧 Python venv | .NET 常驻内存/CPU 远低于 Python+PySide6 |
| 左下**聊天栏变化太快、意义不大** | ROI 只框列表；标定后校验横向区域数，>1 告警 | 聊天每帧都变，会**永久废掉**「ROI 无变化则复用上帧」 |
| 翻页**无额外信号**、**第 2 页行数显著少** | 翻页判据 = **行数骤降** | 真机 |
| **一页最多 12 行**，很少超过 15 个 | `ListRules.MaxRowsPerPage=12` → ROI 校验 + 超限观测丢弃 | 真机 |
| 神器**经常换玩家**，旧数据应「**多次取不到样就消亡**」，注意**识别容错** | 消亡规则（见 §3.5）+ 名字相似度容错 | 真机 |
| 识别误差导致**重复追踪非常多** | 修解析器 + 置信度过滤 + 按字形边界裁剪 | 跟踪表 **21 → 13 条** |
| **放弃玩家ID**，**某行的数据只能更新某行** | 条目身份 = **`(页, 行号)`** | 13 ↔ 13 **零重复**；顺带删掉整套模糊匹配 |
| 显示**把识别区遮住了一部分** | 叠加移到 ROI 左侧 + 自动守卫 | 重叠面积实测 **0** |

## 3. 关键技术决策

### 3.1 被实测推翻的假设

| 原假设 | 实测 | 修正 |
|---|---|---|
| 暗底亮字，可安全二值化 | 列表区**比周围墙面还亮**（105 vs 50） | 只能靠**梯度/描边** |
| 状态标记在**固定列** | 方括号位置**随名称长度右移** | 改**括号锚定**；**行左边界固定**（≈x1575）可作先验 |
| 系统 OCR（零下载）够用 | 低对比度场景 **0/6 行全乱码** | 换 **PP-OCRv3 ONNX** |
| 「名称+玩家名」做条目身份 | 13 个神器产生 **21 条** | 改**行槽位** |
| 逐行列投影能切出汉字 | 汉字间隙仅 **1~2 px** | `MinGap = 0` |
| 批量推理更快 | 批次 6=1303ms vs 逐行 831ms | **逐行** + 识别节流 1 Hz |
| 预处理能救系统 OCR | 拉伸/二值化/2×放大**全部更差（0 行）** | 不再投入，直接换引擎 |
| **int8 动态量化更快**（2026-10-02） | 只量化到 MatMul（36 个 Conv 未量化），模型 10.2→10.3MB，单行 **9ms→21ms（更慢）** | 放弃动态量化（静态量化需校准，另议） |
| **CPU 上批处理更快**（2026-10-02） | 裸 ORT：batch=12 每行 **34ms** vs 逐行 **9ms**；既有记录 batch=6 也更慢 | **不批处理**，逐行 |
| **int8 静态量化能提速**（2026-10-02） | 37 条真实行校准 + BN 折叠后：输出与 fp32 逐时间步 argmax **一致率仅 62.5%**（解码乱码）；速度 CPU **236 vs 219ms**、DML 墙钟 **245 vs 78ms**（**两者都更慢**） | **放弃 int8**，维持 fp32 + DML + 固定宽 + 全批 |
| **原始 rec 模型权重是 initializer**（2026-10-02） | onnx 里权重存在 **`Constant` 节点**，initializer 数为 0 → 动态/静态量化器都无法正常量化 Conv | 量化前必须 `quant_pre_process` 转 initializer（但精度仍崩，见上） |
| 全链路慢在预处理 | 拆解 12 行 602ms：**CTC 解码 397ms + ONNX Run 144ms + FillInput 53ms** | 修解码与预处理，不碰模型 |

### 3.2 采集与标定
- GDI BitBlt → DIB 段（`IScreenCapture` 可替换；目标后端是 WGC）。
- 框选坐标取自**原始窗口消息 `lParam`**（物理像素）。曾用「当前光标位置」，UI 忙时整体偏移，已修。
- ROI 校验（标定后 + 启动时）：横向区域 >1 / 行数 >12 / ROI 过高 → 告警。
- 自动跟随：ROI 同时存为**窗口相对比例**；跟随结果跑出屏幕即拒绝。

### 3.3 行切分与翻页
- **行方向水平梯度能量 + Otsu** 找文本行（对场景底色不敏感）。
- **等距网格吸附**：行距取自数据（**字高中位数的 1.2~4 倍**，实测 ≈1.76），网格外强梯度判**离群剔除**。评分**惩罚空洞槽位**，否则更细的步长会吸收噪声胜出。
- 翻页判据：**行数骤降**（≤基准 60%）⇒ 疑似翻页。已知过渡帧会误报一次（自愈）。

### 3.4 识别
- 亮字提取：**两段式 Otsu**（单次落在背景内、迭代到收敛劈开字芯）。
- 字形切分：列投影，`MinGap = 0`；可视化工具 `ZeOverlay.Cli --analyze-image --glyphs`。
- **PP-OCRv3 rec，不接检测（det）模型**：行切分已做好，按行裁图送 rec 即可，省掉 DB 检测整套后处理。
  - 模型来源：**PyPI** 的 `rapidocr_onnxruntime`（内置 ONNX）+ `paddleocr`（字典）；GitHub/HF 被墙。
  - 按**字形实际边界**裁剪：按估计边界留空白时 PP-OCR 会在行末**幻觉**出字符，导致每帧换 key。
  - 置信度 <0.6 丢弃（正常行 0.86~0.95）。

### 3.5 解析与跟踪
- 状态括号**不在固定列**：按「内容为 `R` 或纯数字」的括号对锚定，取**最后一个**（避开名称里的括号）。
- 容忍实测 OCR 错误：`]`→`I/l/J`、`[`→`《【`、字间空格、全角字母数字、重复闭括号、首尾括号噪声；
  **兜底**：整段丢括号时退化为「裸 `R` 或 1~2 位数字」（数字后是 `/` 则把整个 `n/m` 跳过）。
- **条目身份 = `(页, 行号)`**，某行只更新该行；**玩家名不参与身份**（但可作为展示项：默认显示在最左的固定宽度列，不影响右侧排版）。
- 消亡规则（**无条件超时**）：某槽位超过 **6 秒**（`Tracking.RowDisappearSeconds`，可配置）没扫到数据 ⇒ **自动消失**，不分页、不看是否可见。
  - 代价：翻到第 2 页或列表消失后，旧条目最多再保留 6 秒（不再长期外推）；翻回第 1 页会重新读到并重建。
  - 另有 `MaxAgeSeconds`（300s）作绝对兜底。
- `uses` **粘滞**：同槽位同神器时没读到 `n/m` 就保留旧值（OCR 会间歇漏读，整行覆盖会闪烁）。
- 冷却**只降不升**（挡 OCR 把小数读丢的尖峰 `3.5s`→`35s`）；但有三种例外必须接受新冷却，否则会卡在就绪或误杀新一件：
  1. **外推已 ≈0 时的再次使用**（1Hz 采样看不到中间的 `[R]` 帧）；
  2. **上一帧未连续观测（`Source=Extrapolated`）**——旧条目被移除后，新神器可能复用同一 `(名称,标号)`；只有连续观测（`Live`）才启用"只降不升"。

### 3.6 名单与叠加
- 名单模糊匹配既是**过滤器**也是**纠错器**；命中则采用名单里的标准写法。
- 阈值 **0.85**：实测 0.6~0.8 时 `黑色瓶中闪电` 会误配名单里的 `紫色瓶中闪电`（只差首字）。
- 名单**为空 = 全部显示**。
- 叠加：置顶 + `WS_EX_TRANSPARENT` 点击穿透；拖动模式临时去掉穿透；位置持久化；
  **绝不能覆盖 ROI**（否则截屏把叠加自己抓进识别区 → 自反馈），已加自动守卫。
- 名单命中缓存/排序的键用 `Shared.TrackerKeys.Identity`：标号身份「名称+标号」、行槽位身份「页+槽位」。
  **不能用 页#槽位**——标号身份下条目会保留"上次所在行位"，不同条目会撞键导致名单匹配串台。
- 排序收尾键用「页 → **标号** → 行位」：同名多神器（爆闪1/爆闪2）在回流后行位会互换，
  按标号排才能和真实 HUD 一样稳定（`OverlaySort`，`Slot` 模式除外）。

### 3.7 调度
采集 2 Hz + **识别 1 Hz**（PP-OCR 12 行约 0.7~0.8 s，跑太密会拖垮采集循环），中间靠**秒级外推**补上。
**自适应提速**：识别到「带服务器标号」的连写服行时，自动提到 **5 Hz 采集 / 200 ms 识别**（列表变化快、要跟手）；括号服沿用配置值。折叠档案后 `CaptureFps/RecognitionIntervalMs` 不再逐帧生效，改由这一运行时开关接管。

### 3.8 多社区服：**逐行自动判断格式**（无档案）
不同社区服的行格式结构性不同，**不需要人工选档案/语法**——按行内容自动分流：

| 格式 | 形态 | 判据 |
|---|---|---|
| 本服 `bracket` | `名称 [R]/[数字] 可选n/m 玩家名` | 含**状态括号**（`[R]` 或 `[数字]`） |
| 社区服 `plain` | `简称+序号 玩家名 状态` | 无状态括号；末尾是 `就绪` / `NNs`（`1.5s` 丢小数取整）/ `n/m` / `∞` |

`Parser.ParseAuto`：先按**括号锚定**解析（且**不带裸状态兜底**，否则社区服连写行的标号数字会被误当冷却）；
无有效括号再走 Plain。Plain：从右取状态、从左取名（非数字段 + 标号数字），中间即玩家名；
标号被 OCR 读丢时用**名表最长前缀**切名（`手电王梦虎`→`手电`+`王梦虎`）。
现实坑：`∞` 被读成孤立 `0`/`8` ⇒ **只把末尾单个 `0`/`8`** 当无限（不能是任意 1~2 位数字，否则冷却 `49s` 丢 `s` 会被误判成就绪、长倒计时跳 `[R]`）；`定位310` 这类离谱标号直接丢弃。

**身份／翻页也自动**：跟踪器按「本帧是否有行带服务器标号」自适配——
带标号 ⇒ `(名称, 标号)` 身份、**不分页**（社区服会回流，槽位不稳）；
无标号 ⇒ 行槽位身份、正常翻页（本服）。标号读丢时按「同名最近槽位」借回标号。
**同类多神器**（`水枪1/2/3`，同名不同标号）：**标号一律采信画面读数**，不做任何「借标号」纠错——「同行位借标号」会把真实兄弟（`大荧光1` 落到原 `大荧光2` 的行位）误并、丢条目；「同名最近槽位借标号」在跨帧时会借到暂时不可见的兄弟。**标号整段读丢（null）时一律跳过该行、不猜**。身份模式**粘性**：只要还有标号身份条目存在就保持标号模式（避免"某一帧标号全丢"时翻成行槽位身份；真正换到无标号服时旧条目超时后自然退出）。

**裁剪**：统一用**行带全宽**（不再紧缩到字形）。社区服的简称列又小又暗，紧缩会把它整列裁掉
（真机视频样本实测：只剩玩家名+状态 ⇒ 解析失败）；全宽对本服也实测 12/12。

**名表**（`config.json.Vocabulary`）：用于 Plain 切名与挡 OCR 读花（`优火盐`/`正位`）。
新装预置两服并集。**ROI 只有一份**：切服时重新框选（`Ctrl+Shift+R`）；同窗口内的移动由相对跟随处理。

## 5. 尚未实现的设计意图

### M5 交互层
- **设置面板常驻预览窗口左列**（非弹窗，已取消独立设置窗口与「设置」按钮），三个页签，点「应用设置」后即时生效：
  - **关注名单**：增删（≤10）、显示顺序上下移、模糊阈值、一键加入「最近识别」。
  - **显示**：排序方式（名单顺序 / 页-行 / 就绪优先+冷却升序 / 名称）、字号、背景不透明度、显示剩余次数、`#页-行` 前缀、**玩家名（最左固定宽度列，默认开）**、**无数字标号时按类编号（滋水枪1、滋水枪2…，紧跟名称、同色）**、**行间距可调**、**未扫描到标记 `~`（置于最左、与正文同字形占位）**、统一正文色 / 标记色（不再按来源换色）。
  - **频率**：采集频率（1–10 Hz）、识别间隔（200–5000 ms）、行消失超时（0.5–60 s，默认 6 s，即时生效）。
  - **热键**：6 个动作可直接按键录入组合键（至少一个修饰键），保存后整组重注册并按候选回退。
- 排序是**纯逻辑** `Shared.OverlaySort`（可单测）；Host 只提供名称与名单名次。

### M6 性能与打包
- 已落地：`Cache`（相同像素复用行分析）、CTC 解码改读底层 span、`FillInput` 预计算列并直写 buffer → 12 行 **602ms → ~150ms**（CPU）。
- 进一步：**DirectML + 固定宽 640 + 全批 12 → ~70ms**（比 CPU 快 ~2.1×）；`Recognition.ExecutionProvider` 默认 `directml`，会话创建失败**自动回退 CPU**；代价 +~23MB 与 DX12 依赖。
- **被否掉的路**（别再走）：
  - **动态 int8 量化**：该模型 36 Conv，`quantize_dynamic` 只量化 MatMul，模型不变小且更慢（单行 9→21ms）。要 int8 必须**静态 + 校准集**。
  - **静态 int8 量化**（2026-10-02，`tools/quantize-ppocr-static.py`）：用 37 条真实行校准、`quant_pre_process` 折叠 BN、只量化 `Conv,MatMul` 后可加载，但**精度崩**（与 fp32 逐时间步 argmax 一致率 62.5%）且**两个 EP 都更慢**（CPU Run 236 vs 219ms，DML 墙钟 245 vs 78ms）。**放弃 int8**。
    - 附加坑：原始模型权重存在 `Constant` 节点，量化器需先 `quant_pre_process` 转 initializer；逐元素算子被量化还会让 C# ORT 报 `QLinearMul ... must be a scalar`。
  - **CPU 批处理**：batch=12 每行 34ms vs 逐行 9ms。
  - **DML 不固定宽度**：逐行宽度不同 → 反复重编译算子，慢 3×。
- 关键事实：
  - DML EP 需把 `Microsoft.AI.DirectML` 的 win-x64 `DirectML.dll` 复制到 exe 旁（传递依赖，targets 不自动导入），否则崩 `0x80070057`。
  - ORT 工作线程在两次 Run 间自旋会白占 CPU → `Recognition.AllowSpinning=false`（默认）。
  - 本机 `Process.TotalProcessorTime` 失真，**绝对 CPU 数字不可信**，需真机复测。
  - CUDA 方案体积 **+约 2.4GB**（ORT CUDA EP 643MB + cuBLAS 753 + cuDNN 961），性价比低。
- **打包**：自包含单文件夹（win-x64）已落地，`tools/publish.ps1` 发布 + `tools/install.ps1` 安装；剔除运行时无用的 det 模型与 pdb；实测文件夹 214.9 MB / zip 91.8 MB，单文件夹下 DML 正常加载。另有**单文件自解压安装器** `tools/make-installer.ps1`（Windows 自带 IExpress）：约 90.7 MB，用户自选路径、自动展开 283 文件并建快捷方式。详见 `PACKAGING.md`。
- 待做：输入宽度收敛 / ONNX arena 收敛；自定义图标与代码签名。
